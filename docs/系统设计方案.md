## 1 系统分析

### 1.1 项目背景与目标

机房（数据中心/实验室机房）对运行环境有严格要求：温度过高导致设备过热降速，湿度过高引发凝露短路、过低产生静电，烟雾是火灾早期最关键的前兆指标，光照可辅助判断机房照明与人员活动状态。传统人工巡检无法做到 7×24 实时监测。

本系统基于**串口通信 + TCP/IP 网络通信**技术，构建"感知—传输—存储—分析—告警"完整链路：

- 单片机实时采集机房温度、湿度、烟雾浓度、光照强度；
- 通过**串口**上传至客户端计算机；
- 客户端通过 **TCP Socket** 转发至远程 Linux 服务器；
- 服务器将数据存入 **MySQL** 数据库，并进行统计分析（均值/最值/方差/超标统计），超阈值时**回传告警**；
- 客户端实时显示数据曲线与告警信息。

### 1.2 功能需求

| 编号 | 功能 | 归属模块 |
|---|---|---|
| F1 | 多传感器实时采集（温度/湿度/烟雾/光照，2s周期） | 单片机 |
| F2 | 按自定义帧协议通过 UART 上报数据 | 单片机 |
| F3 | 串口配置（COM口/波特率）、数据接收与校验 | 客户端 |
| F4 | 串口数据解析、实时数值与历史曲线显示 | 客户端 |
| F5 | TCP 连接服务器、数据转发、断线重连 | 客户端 |
| F6 | 接收服务器下发的分析结果与告警并展示 | 客户端 |
| F7 | select 模型 + 多线程并发处理多客户端连接 | 服务器 |
| F8 | 数据入库 MySQL | 服务器 |
| F9 | 定时分析：均值/最大/最小/方差/超标次数 | 服务器 |
| F10 | 超阈值告警生成与推送 | 服务器 |
| F11 | 运行日志与通信原始数据记录（调试依据） | 三端 |

### 1.3 非功能需求

- 数据端到端延迟 ≤ 1s（正常网络）；
- 客户端与服务器断线自动重连（指数退避，最长 30s）；
- 串口误帧可检测（校验和）、可恢复（帧头重同步）；
- 服务器支持 ≥ 10 个客户端并发（select FD 上限足够）；
- 可扩展：传感器类型、协议帧通过"类型字段"扩展，不修改帧结构。

## 2 系统总体设计

### 2.1 总体架构

```
DHT11 ─┐
MQ-2  ─┼─ 单总线/ADC/I2C → STM32F103C8T6 ─ UART(USB转TTL) → Windows客户端(Qt5)
BH1750─┘                                              │
                                                      TCP Socket
                                                      ↓
                              Linux服务器(VMware Ubuntu)
                              ├─ select I/O 多路复用 + 多线程
                              ├─ MySQL 数据库
                              └─ 分析线程（定时统计/告警）
                                      │
                              分析结果 / 告警 ──TCP──→ 客户端显示
```

### 2.2 模块划分与数据流

| 模块 | 技术栈 | 职责 |
|---|---|---|
| ① 感知与下位机 | STM32F103C8T6（标准库，Keil MDK） | 传感器驱动、数据帧打包、UART 发送 |
| ② 客户端 | Qt 5（C++，QSerialPort + QTcpSocket + QCustomPlot） | 串口收发、协议解析、TCP 转发、曲线显示、告警展示 |
| ③ 服务器 | Ubuntu Linux（C，POSIX socket + pthread + MySQL C API） | select 并发、数据入库、统计分析、告警推送 |

**数据流**：传感器 → STM32（组帧）→ 串口 → 客户端（校验/解析/显示）→ TCP → 服务器（解析/入库）→ 分析线程（统计）→ 告警/结果 → TCP 回传 → 客户端展示。

## 3 通信协议设计

### 3.1 串口通信协议（单片机 → 客户端）

**物理层参数**：UART，115200-8-N-1，经 USB转TTL 模块连接 PC。

**帧格式（变长帧）**：

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2B | `0xAA 0x55`，用于帧同步/抗粘包 |
| 帧类型 | 1B | `0x01`=传感器数据帧，预留 `0x02`=心跳、`0x03`=应答 |
| 数据长度 | 1B | 数据域字节数 N |
| 数据域 | NB | 见下 |
| 校验和 | 1B | 从"帧类型"到"数据域末尾"逐字节累加和的低8位 |

**数据帧数据域**：

```
传感器个数 n (1B) + n × ( 传感器类型(1B) + 数据值(2B, 大端) )
类型: 0x01温度 0x02湿度 0x03烟雾(ADC原始值) 0x04光照(lux)
数值: ×10 后的带符号整数(int16)，如 25.6℃ → 0x0100
```

示例：温度 25.6℃、湿度 55.0%、烟雾 ADC=312、光照 356 lux →
`AA 55 01 0D 04 01 0100 02 0226 03 0138 04 0164 <checksum>`

**可靠性设计**：客户端收到数据后先搜帧头 → 验长度 → 验校验和，任一失败则丢弃至下一帧头位置（重同步机制），保证误码不扩散。

### 3.2 应用层网络协议（客户端 ↔ 服务器，TCP）

采用**文本协议 JSON + 换行符 `\n` 分帧**（可读性好，便于调试演示；粘包处理简单——按 `\n` 切分缓冲区）。

| 方向 | 消息 | 格式示例 |
|---|---|---|
| C→S | 登录 | `{"type":"LOGIN","client_id":"PC-01"}` |
| S→C | 登录应答 | `{"type":"LOGIN_ACK","status":0}` |
| C→S | 数据上报（2s周期） | `{"type":"DATA","ts":"2026-09-28 15:00:01","sensors":[{"id":1,"v":25.6},{"id":2,"v":55.0},{"id":3,"v":312},{"id":4,"v":356}]}` |
| C→S | 心跳（30s周期） | `{"type":"HEARTBEAT"}` |
| S→C | 分析结果推送 | `{"type":"ANALYSIS","period":"10min","sensors":[{"id":1,"avg":24.1,"max":26.8,"min":22.3,"std":1.2,"over_cnt":3}]}` |
| S→C | 告警推送 | `{"type":"ALARM","level":"HIGH","sensor":1,"value":35.2,"threshold":30.0,"msg":"温度超上限","ts":"..."}` |

**状态机**：客户端 `断开 → 连接中 → 已登录 → 在线（收发）`；心跳超时（90s 无 DATA/HEARTBEAT）服务器主动断开并回收资源。

## 4 数据库设计（MySQL）

```sql
CREATE DATABASE machine_room DEFAULT CHARSET utf8mb4;

-- 原始数据表
CREATE TABLE sensor_data (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  client_id    VARCHAR(32)  NOT NULL,
  sensor_type  TINYINT      NOT NULL COMMENT '1温度 2湿度 3烟雾 4光照',
  sensor_value DECIMAL(10,2) NOT NULL,
  collect_time DATETIME     NOT NULL,
  KEY idx_time (collect_time)
);

-- 分析结果表
CREATE TABLE analysis_result (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  client_id    VARCHAR(32) NOT NULL,
  sensor_type  TINYINT     NOT NULL,
  period_start DATETIME    NOT NULL,
  period_end   DATETIME    NOT NULL,
  avg_value    DECIMAL(10,2),
  max_value    DECIMAL(10,2),
  min_value    DECIMAL(10,2),
  std_value    DECIMAL(10,2),
  over_count   INT DEFAULT 0,
  created_time DATETIME   NOT NULL
);

-- 告警日志表
CREATE TABLE alarm_log (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  client_id  VARCHAR(32) NOT NULL,
  sensor_type TINYINT    NOT NULL,
  value      DECIMAL(10,2),
  threshold  DECIMAL(10,2),
  level      VARCHAR(8) COMMENT 'LOW/MID/HIGH',
  alarm_time DATETIME   NOT NULL
);

-- 阈值配置表（服务器内存中亦缓存一份）
CREATE TABLE threshold_cfg (
  sensor_type TINYINT PRIMARY KEY,
  min_value   DECIMAL(10,2),
  max_value   DECIMAL(10,2),
  level       VARCHAR(8)
);
```

初始阈值（机房标准 GB50174 参考）：温度 18~26℃、湿度 40%~60%RH、烟雾 ADC > 400（高危）、光照仅记录不告警。

## 5 各模块详细设计

### 5.1 单片机端（STM32F103C8T6，标准库）

**引脚分配**：

| 外设 | 引脚 | 接口 |
|---|---|---|
| DHT11 | PB5 | 单总线 GPIO |
| MQ-2 | PA0 | ADC1 通道0（12位） |
| BH1750 | PB6/PB7 | I2C1（SCL/SDA） |
| UART1→PC | PA9/PA10 | TX/RX 115200 |

**软件结构（前后台）**：

```
main: 时钟/GPIO/ADC/I2C/UART初始化 → 循环{ SysTick 2s到 → 采集全部传感器 → 组帧 → UART发送 }
dht11.c: 单总线时序（主机起始→响应→40bit读取→校验）
mq2.c:   ADC采样8次中值滤波 → 原始值
bh1750.c: I2C读2字节 → lux换算
frame.c: 组帧/校验和计算（与协议3.1一致）
usart1.c: printf重定向 + 发送函数
```

### 5.2 客户端（Qt 5，Windows）

**工程结构**：

```
client-qt/
├── main.cpp
├── mainwindow.ui        # 主界面
├── serialworker.cpp/h   # 串口线程：收原始字节流→帧解析→emit dataReady(传感器数据)
├── netclient.cpp/h      # QTcpSocket：登录/上报/重连（指数退避）
├── plotpanel.cpp/h      # QCustomPlot 四通道实时曲线
└── protocol.cpp/h       # 串口帧解析器 + JSON 组包（与服务器协议一致）
```

**线程模型**：主线程 UI；`SerialWorker` 移入 `QThread`（阻塞式读串口）；`QTcpSocket` 在主线程（异步信号槽）。串口数据经**信号槽**（queued connection）跨线程传递，避免共享数据加锁。

**界面布局**：左侧串口/连接配置区（COM口、波特率、服务器IP:Port、连接按钮）；中部四路实时数值 + QCustomPlot 曲线；底部日志区（原始HEX、解析结果、服务器消息）与告警弹窗。

### 5.3 Linux 服务器（VMware Ubuntu，C + pthread + MySQL C API）

**并发模型（多线程 + select）**：

```
主线程: listen(fd) → select() 监听 {监听socket + 已连接客户端fd}
        ├─ 新连接 → accept → 加入fd_set → 创建会话结构体
        ├─ 可读   → 读取该fd数据 → 投递到任务队列
        └─ 异常   → 关闭连接、清理会话
工作线程池(×4): 从任务队列取任务 → JSON解析 → 入库 → 阈值检查(产生告警→回写fd)
分析线程: sleep(60s) → SELECT 近10min数据 → 计算 avg/max/min/std/over_cnt
          → 写analysis_result → 生成ANALYSIS消息推送给在线客户端
```

**关键点**：fd_set 与会话表由互斥锁保护（主线程修改，工作线程只读副本）；select 超时 1s 保证新连接及时注册；MySQL 连接由连接线程独占或使用连接池（简化：任务线程内申请/释放连接，配 `mysql_thread_init`）。

## 7 联调与测试方案

**分层测试（自底向上）**：

1. **单片机级**：串口助手验证帧格式逐字节正确（对照§3.1示例）；传感器数值与实际环境比对；
2. **客户端级**：先用"数据模拟器"（本项目 simulator/，模拟STM32按协议发帧）替代真机，验证解析/曲线/重连；
3. **服务器级**：用 `nc`/telnet 手工发JSON验证入库与分析；
4. **端到端**：模拟器→客户端→服务器全链路；再换真机；
5. **异常测试**：拔串口、断网重连、并发3+客户端、发送错误校验帧、粘包帧。

**虚拟机网络配置**：VMware 使用 **NAT + 端口转发**（宿主机 9000 → 虚拟机 9000）或 **桥接模式**（虚拟机与宿主机同网段直连）；防火墙放行 9000/tcp 与 MySQL 3306 仅限本机。

**调试记录**：三端各维护 `debug-log.md`，按"现象→定位→原因→解决"四要素记录，直接作为报告《程序调试报告》素材。

## 8 风险与应对

| 风险 | 概率 | 应对 |
|---|---|---|
| BH1750/MQ-2 硬件缺失或损坏 | 中 | 协议可变帧天然支持裁剪：仅保留DHT11两路，代码改宏开关即可 |
| 国庆假期无法到实验室 | 高 | 数据模拟器 + 虚拟串口（com0com），在家全链路联调 |
| select 高并发性能 | 低 | 本场景 <10 连接，select 完全够用；报告中讨论与epoll差异即可 |
| Qt 环境问题 | 中 | 统一使用 Qt 5.12 + MinGW 套件，或 MSVC2017；QCustomPlot 单头文件库免编译 |
| VMware 网络不通 | 中 | 优先桥接；备选 NAT 端口转发；极端情况宿主机临时充当服务器验证 |
