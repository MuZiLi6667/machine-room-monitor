# 服务器端运行说明（任务C）

> 本文档面向"拿到虚拟机就要把服务器跑起来"的人，按 §0 走即可在 5 分钟内跑通。
> **交付状态：S8 交付版**（开发过程 S0~S8 的每个问题见 `docs/调试记录-C.md`）。
> 接口依据：`docs/接口规范.md`（JSON 字段、表结构、端口、阈值**未做任何改动**）。

服务器能力一览（全部已实现并验收）：

| 能力 | 说明 |
|---|---|
| select 多连接 | 单线程 select 主循环管所有连接，按 `\n` 分帧，超长行（>4KB）丢弃 |
| 线程池 | 4 个工作线程 + 有界任务队列；主线程只做收发/投递，业务全在工作线程 |
| 会话协议 | LOGIN（重复登录踢旧）、HEARTBEAT 应答、**90s 无消息超时回收** |
| DATA 入库 | 一条 DATA 拆成每传感器一行写 `sensor_data`，`ts` 缺省/非法时用服务器 `NOW()` |
| 阈值告警 | 启动时加载 `threshold_cfg`，超标即推 ALARM 并写 `alarm_log`（不去重） |
| 周期统计 | 分析线程每 60s 统计最近 10 分钟数据写 `analysis_result`，并向在线客户端推 ANALYSIS |
| 启动参数 | `-p 端口 -t 分析周期 -w 统计窗口`（默认 9000/60/600），非法参数直接退出 |

---

## 0 五分钟跑起来（TL;DR）

干净 Ubuntu（20.04/22.04）上从零到能收数据：

```bash
# ① 依赖（一次性，需要 sudo）
sudo apt update && sudo apt install -y build-essential mysql-server libmysqlclient-dev
sudo ufw allow 9000/tcp                 # 若启用了 ufw

# ② 初始化数据库（一次性；脚本要建库+建用户，需要 sudo）
cd ~/server-linux
sudo mysql < sql/init.sql

# ③ 编译（产出 ./server）
make

# ④ 启动（前台跑；停止按 Ctrl-C）
./server
```

服务器打印「服务器已就绪，按 Ctrl-C 退出」后，**另开一个终端**用仓库里的假客户端压数据：

```bash
python3 simulator/server_probe.py client -H 127.0.0.1 --id PC-01
# 假客户端与服务器不在同一台机器时（例如宿主机连虚拟机），把 127.0.0.1 换成虚拟机 IP：
# python3 simulator/server_probe.py client -H <虚拟机IP> --id PC-01
#   查 IP：在虚拟机里敲 ip -br addr —— ens33 是桥接地址（队友联调用），ens37 是 NAT 地址（仅宿主机可用）
```

看到这些就算通了：

| 观察位置 | 应该看到 |
|---|---|
| probe 终端 | `[<-] {"type":"LOGIN_ACK","status":0}`，之后每 2 秒 `[-> #n]` 一条 DATA |
| probe 终端 | 数值超阈值的 DATA 会立刻收到 `[<-] {"type":"ALARM",...}` |
| 服务器日志 | `[工作线程] ... 入库 4/4 行（跳过 0）` |
| 服务器日志 | 满 60 秒出现 `分析：窗口 … 共 N 组、入库 N 行；在线 1 个客户端，推送 1 个` |
| 数据库 | `mysql -uiot -piot123456 machine_room -e "SELECT COUNT(*) FROM sensor_data;"` 行数持续增长 |

各步骤的细节与判读口径见 §1~§5，稳定性与内存检测见 §5.6/§6，出问题查 §7。

## 2 数据库初始化（只做一次）

库、表、阈值初始数据与程序用的 `iot` 用户都在 `sql/init.sql` 里。该脚本要建库建用户，**需要 MySQL 的管理员权限**：

```bash
cd ~/server-linux
sudo mysql < sql/init.sql
```

验证（应列出 4 张表与 3 行阈值）：

```bash
mysql -uiot -piot123456 machine_room -e "SHOW TABLES;"
mysql -uiot -piot123456 machine_room -e "SELECT * FROM threshold_cfg;"
```

> MySQL 与 ssh 都是开机自启，**正常开机后无需手动启动**，可用 `systemctl status mysql` 确认。
> 脚本可重复执行（建库建表都是 `IF NOT EXISTS`，阈值是 upsert）。
>
> **重导/清库**（验收或换数据时）：`iot` 账号的授权是 `machine_room.*` 的全部权限，
> 所以删库重建不必再要管理员权限：
> ```bash
> mysql -uiot -piot123456 -e "DROP DATABASE machine_room;"    # iot 的授权里含 DROP
> mysql -uiot -piot123456 < sql/init.sql                     # 重导：4 张表 + 3 行阈值为空库重建
> ```
> 此时脚本会在**第 4 段（建用户）**中止并报 `ERROR 1227 (42000) at line 69: Access denied; you need
> (at least one of) the CREATE USER privilege(s) for this operation`——`iot` 没有 `CREATE USER` 权限，
> 属**正常现象**：前 3 段（库/表/阈值）已经执行完，`iot` 用户也早已存在、无需重建。
> 只想清数据不想重建表结构，更简单的做法是：
> `mysql -uiot -piot123456 machine_room -e "TRUNCATE sensor_data; TRUNCATE alarm_log; TRUNCATE analysis_result;"`。

## 3 编译

```bash
cd ~/server-linux
make            # 产出 ./server
```

`Makefile` 用 `wildcard` 自动收录 `src/*.c`，后续新增模块无需改它。`-Wall -Wextra` 要求**零警告零错误**。
代码有改动时先 `make clean && make`，避免残留目标文件。

## 4 启动与停止

### 4.1 前台运行（推荐日常调试）

```bash
cd ~/server-linux
./server                          # 默认：端口 9000、分析周期 60s、统计窗口 600s
./server -p 9000 -t 60 -w 600     # 显式写法（三项都可省略，省略即用默认值）
./server -t 15 -w 60              # 联调期缩短周期，15 秒就能看到一条 ANALYSIS
```

| 参数 | 含义 | 默认 | 取值范围 |
|---|---|---|---|
| `-p` | 监听端口 | 9000 | 1~65535 |
| `-t` | 分析周期（秒） | 60 | 1~86400 |
| `-w` | 统计窗口（秒） | 600 | 1~604800 |

参数非法（非数字、越界、未知选项）会打印用法并**直接退出**，不会带着坏配置启动。
`-w` 小于 `-t` 时能跑，但相邻两期的窗口不重叠、两期之间的数据不会被统计——只在临时调试时这么用。

成功时输出（启动横幅会打印**实际生效**的端口与周期/窗口）：

```
版本 S8 交付版：LOGIN/心跳/超时 + DATA 入库 + 阈值告警 + 周期统计
监听 socket 就绪：0.0.0.0:9000（fd=4, backlog=64）
服务器已就绪，按 Ctrl-C 退出
分析线程已启动：每 60s 统计一次，窗口 600s，仅推送给在线客户端
```

日志直接打在终端上（带时间戳、级别、线程号）。**停止：按 `Ctrl-C`**，会依次打印「select 主循环已退出」→「分析线程已收到退出请求，退出」→「数据库连接已关闭」→「收到退出信号，服务器正常退出」，并释放 9000 端口。

### 4.2 后台常驻（需要腾出终端时）

```bash
cd ~/server-linux
nohup setsid ./server > /tmp/server.log 2>&1 < /dev/null &
tail -f /tmp/server.log          # 看日志；Ctrl-C 只退出 tail，不影响服务器
```

停止后台实例（**用 `-INT` 走优雅退出，且绝不要加 `-f`**）：

```bash
pkill -INT -x server
pgrep -ax server                 # 应无输出
ss -ltn | grep 9000              # 应无输出
```

> **一次只发一条启动命令，并用 `timeout N ssh …` 包裹**：通过 ssh 起的后台进程会占住会话，
> 未包裹的 ssh 要等服务器退出才返回，后面排队的启动命令会在那一刻"补位"把服务器又拉起来
> （看起来像服务器自己重启了，见调试记录问题 41）。

### 4.3 开机 / 关机（虚拟机层面）

```bash
# 开机（宿主机执行）
"D:/Virtual Machine/vmrun.exe" start "D:/VMs/Ubuntu/Ubuntu.vmx" nogui

# 关机（先在虚拟机内停服务器，再在宿主机执行）
"D:/Virtual Machine/vmrun.exe" stop "D:/VMs/Ubuntu/Ubuntu.vmx" soft
"D:/Virtual Machine/vmrun.exe" list      # 确认 Total running VMs: 0
```

`soft` 是 ACPI 优雅关机；**不要用 `hard`**（等同拔电源，可能损坏文件系统）。

## 5 自测与联调

### 5.1 确认在听

```bash
ss -ltn | grep 9000               # 应有一行 LISTEN
ip -br addr show ens33            # 当前桥接 IP（校园网 DHCP，可能变动，联调时以实际为准）
```

### 5.2 手测三条标准向量

虚拟机上装有 `nc`，可交互测试（`<>` 内为实际 IP）：

```bash
nc 127.0.0.1 9000
{"type":"LOGIN","client_id":"PC-01"}        ← 应回 {"type":"LOGIN_ACK","status":0}
{"type":"HEARTBEAT"}                        ← 应回 {"type":"HEARTBEAT_ACK"}
```

DATA 向量（见接口规范 §3.3）发出去**不会有应答**（规范未定义应答），要在服务器日志与数据库里看效果：

```
fd=4 client_id=PC-01 DATA：ts=2026-09-28 15:00:01 入库 4/4 行（跳过 0）[1=25.6 2=55 3=312 4=356]
```

```bash
mysql -uiot -piot123456 machine_room -e "SELECT * FROM sensor_data ORDER BY id DESC LIMIT 4;"
# 应看到 4 行（sensor_type 1~4），collect_time 即该条 DATA 的 ts
```

错误 JSON 的处理（接口规范 §3.2，回 ERROR 但**不断连**）：

```
{bad                       ← {"type":"ERROR","code":1,"msg":"malformed json"}
{"type":"PING"}            ← {"type":"ERROR","code":2,"msg":"unknown type"}
```

### 5.3 用假客户端跑联调

```bash
# 支持 Python 的机器上（含宿主机），<虚拟机IP> 换成实际地址：
#   宿主机自己跑     → 用 NAT 地址（VMware 分配，固定不变，只有宿主机能连）
#   队友从别的机器跑 → 用桥接地址（校园网 DHCP，会变；虚拟机里 ip -br addr show ens33 查）
python3 simulator/server_probe.py client -H <虚拟机IP> --id PC-01
```

它登录后每 2s 发一条 DATA（4 个传感器），服务器每条约写 4 行，可在库里查到 `sensor_data` 行数随之增长：

```bash
mysql -uiot -piot123456 machine_room -e "SELECT COUNT(*) FROM sensor_data;"
```

### 5.4 告警自测（S5）

阈值初值：温度 18~26(HIGH)、湿度 40~60(MID)、烟雾 ≤400(HIGH)、**光照不告警**。登录后发一条超标的 DATA，应立即收到 ALARM：

```
{"type":"DATA","ts":"2026-09-28 15:00:01","sensors":[{"id":1,"v":35.2}]}
← {"type":"ALARM","level":"HIGH","sensor":1,"value":35.2,"threshold":26,"msg":"温度超上限","ts":"2026-09-28 15:00:01"}
```

`threshold` 是**被越过的那个边界**（超上限给 max、低于下限给 min）；每条超标 DATA 都告警一次（不去重）。
判定用**严格不等号**：值恰好等于边界不算超标。

```bash
mysql -uiot -piot123456 machine_room -e "SELECT * FROM alarm_log ORDER BY id DESC LIMIT 3;"
```

> **改阈值要重启服务器**：`threshold_cfg` 只在启动时读一次（`db_load_thresholds`），改表后需 `pkill -INT -x server` 再 `./server`。

### 5.5 分析结果自测（S6）

服务器每 `-t` 秒（默认 60）统计最近 `-w` 秒（默认 600）的数据，按 `client_id × sensor_type` 聚合写 `analysis_result`，并给**当前在线**的客户端推一条 ANALYSIS（字段见接口规范 §3.1）：

```
← {"type":"ANALYSIS","period_start":"2026-09-22 20:25:36","period_end":"2026-09-22 20:25:36","sensors":[{"id":1,"avg":24.93,"max":29.8,"min":18.6,"std":3.77,"over_count":9}, …]}
```

口径说明（联调时按这几条判读）：

- `avg/max/min/std` 按 `analysis_result` 的列精度（`DECIMAL(10,2)`）规整后推送，**与库里查到的值一致**；
- `std` 在"窗口内只有一个样本"时给 **0**，不是 null；
- `over_count` 是窗口内该组超过阈值的条数，判定口径与 ALARM 完全一致（严格越界、阈值表里为 NULL 的一侧不检查、光照不告警故恒为 0）；
- **无数据的周期不写库、也不推送**（不会给客户端发空的 `sensors` 数组）；
- **不在线的 client 只入库、不推送**：客户端断开后，它窗口内的数据仍会被后续周期统计进 `analysis_result`，只是没人收推送。

排查用 SQL：

```bash
mysql -uiot -piot123456 machine_room -e "SELECT * FROM analysis_result ORDER BY id DESC LIMIT 8;"
```

要核对某一期的统计是否算对了，用那一行的 `period_start/period_end` 手工复现同一窗口：

```sql
SELECT client_id, sensor_type, AVG(sensor_value), MAX(sensor_value), MIN(sensor_value),
       STDDEV_POP(sensor_value), COUNT(*)
FROM sensor_data
WHERE collect_time >= '<period_start>' AND collect_time <= '<period_end>'
GROUP BY client_id, sensor_type;
```

> 统计按 `collect_time` 过滤，窗口**两端都是闭区间**：带"未来 ts"的 DATA 会落在窗口外（不会被算进任何一期），
> 手工复现时不要把它当成"少数了一行"。

### 5.6 稳定性自测（S7 已做，结论如下）

| 检查 | 做法 | S7 实测结论 |
|---|---|---|
| 3 客户端并发 | 3 个 probe 同时跑 10 分钟 | 无崩溃；每 client 1200 行、12 组计数全相等；跨域查询 0 行（数据互不串）；`[ERROR]` 计数 0 |
| fd / 内存稳定 | 压测中两次 `ls /proc/$(pgrep -x server)/fd \| wc -l`、`lsof -p <pid> \| wc -l` | `fd 12→12`、`lsof 28→28`、RSS `8504KB→8504KB`，差值全 0；断开后回落到底线 |
| 异常断开（kill -9） | 宿主机强杀一个 probe | 服务器 1 秒内回收（强杀由内核发 RST，`recv()` 立刻返回）；其余客户端不受影响 |
| 90s 超时 | 客户端 `kill -STOP` 冻结（socket 保持打开、不再响应） | 最后一条消息后**正好 90 秒**被回收，日志有「会话超时」记录 |
| 半行重连 | 发半截 JSON（不换行）后断开，再重连登录 | 半行只进缓冲、不产生任何处理；重连 LOGIN_ACK 正常、后续 DATA 全部入库 |

## 6 内存与并发检测（判读口径）

虚拟机没装 valgrind 也能跑——`apt-get download` 不需要 root：

```bash
cd /tmp && apt-get download valgrind && mkdir -p /tmp/vg && dpkg-deb -x valgrind_*.deb /tmp/vg
export VALGRIND_LIB=/tmp/vg/usr/lib/x86_64-linux-gnu/valgrind
/tmp/vg/usr/bin/valgrind --tool=memcheck --leak-check=full --log-file=/tmp/mc.log ./server
```

跑一轮收发（登录/DATA/告警/心跳/非法 JSON + 跨过一个分析周期）后 **`Ctrl-C` 优雅退出**，看报告：

```
definitely lost: 0 bytes in 0 blocks          ← 必须为 0
indirectly lost: 0 bytes in 0 blocks          ← 必须为 0
  possibly lost: 117,192 bytes in 92 blocks   ← 正常形态，不是泄漏（见下）
```

- **判读口径：只认 `definitely lost` 与 `indirectly lost`，两者都应为 0。**
- `possibly lost: 117,192 bytes in 92 blocks` 是 **4 个常驻工作线程的 TLS（4×320 字节）+ 各自一条 MySQL 连接（4×28,978 字节）**，
  每条 loss record 都写着 "in 4 blocks"。工作线程没有 join 机制、随进程退出回收，这是既定形态，**不要去消除它**。
- 分析线程的连接**曾经**是 `definitely lost`（1,192 + 27,786 字节）：它被 `pthread_join` 真回收，TLS 随线程销毁，
  连接不先关就成了没人指向的内存。S8 已修（`analysis_thread` 退出前调 `db_close_this_thread()`），复测归零。

> **停 valgrind 实例必须用 PID**：它运行后的进程名是 `helgrind-amd64-`（被截断），
> `pkill -x valgrind` / `pkill -x server` 都匹配不到，会把"没杀掉任何进程"误读成"已经退出"。
> ```bash
> PID=$(pgrep -f '[v]algrind.bin'); kill -INT $PID     # valgrind 会把 SIGINT 转发给服务器
> ```
> 服务器走完优雅退出后，valgrind 才会把报告写完整；直接 `kill -9` valgrind 则报告不全。

数据竞争检测同理：`--tool=helgrind --log-file=/tmp/hg.log ./server`，实测 0 竞争
（4 个工作线程并发解析、分析线程退出、并发首次建连三条路径都覆盖）。

## 7 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `bind() 端口 9000 失败：Address already in use` | 已有实例在跑：`pgrep -ax server` 后 `pkill -INT -x server`（TIME_WAIT 残留由 `SO_REUSEADDR` 处理，不需要等） |
| 队友连不上 9000 | ① `ss -ltn \| grep 9000` 确认在听；② `ip -br addr` 看桥接 IP 是否变了；③ 若启用了 ufw，`sudo ufw allow 9000/tcp` |
| 虚拟机 ping 得通但 ssh 连不上 | `ping` 的统计行会骗人（目标不可达时仍报 0% 丢失），**以 ssh 端口为准** |
| `pkill -f 'server-linux/server'` 把执行命令的 shell 也杀了 | `-f` 匹配整条命令行，连自己一起杀。**只按进程名 `pkill -x server`** |
| 启动即退出，日志 `数据库初始化失败：iot@localhost/machine_room 连不上` | S4 起数据库是**启动硬依赖**：先 `systemctl status mysql` 确认在 running，再确认已执行过 `sql/init.sql`（建库建用户）。认证失败多为脚本没跑过或用户密码不符——`init.sql` 建用户时已显式用 `mysql_native_password`（MySQL 8.0 默认插件会导致登录失败） |
| 启动日志里 `本线程已建立 MySQL 连接` 出现多次 | 正常：S4 起**每个线程一条 MySQL 连接**（主线程 + 4 个工作线程 + 分析线程，最多 6 条），跑 probe 时 `information_schema.processlist` 里能看到这些 `iot` 连接 |
| 日志 `[ERROR]` 计数看着很多 | 用 `grep -c '\[ERROR\]'` 匹配**级别字段**；`grep 'ERROR'` 会把正文里"回 ERROR code=…"的 INFO/WARN 也算进去（假阳性） |
| `grep 'ANALYSIS'` 数出来的条数偏多 | 脚本自己的汇总行里也含 "ANALYSIS" 字样，筛报文要带引号：`grep '"ANALYSIS"'` |
| 日志停在「分析：窗口 … 内无数据，本周期不写 analysis_result」 | 正常：该窗口内一条 DATA 都没有（客户端都断了、旧数据也过了窗口），既不写库也不推送 |
| 客户端收不到 ANALYSIS | 依次查：① 这台客户端在窗口内有没有数据（刚登录的要等下一个有数据的周期）；② 连接是否还活着（推送只发给当前在线的会话）；③ `ps -ef \| grep server` 看实际启动参数，确认 `-t/-w` 没被改小 |
| 客户端时间戳比服务器"慢" 2 秒 | 虚拟机时钟比宿主机快约 2 秒。**判读时间戳一律用同一侧时钟**，别拿宿主机的墙钟对数据库里 `NOW()` 写的时间 |

更多排查过程见 `docs/调试记录-C.md`（S0~S8 的每个坑都有"现象→定位→原因→解决"）。
