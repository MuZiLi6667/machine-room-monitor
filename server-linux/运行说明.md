# 服务器端运行说明（任务C）

> 本文档面向"拿到虚拟机就要把服务器跑起来"的人。
> 当前进度：**S6 已完成**（连接 → LOGIN → HEARTBEAT → 超时回收 的会话链路可用；DATA 拆包写入 `sensor_data`；超阈值推送 ALARM 并写 `alarm_log`；分析线程每 60s 统计最近 10 分钟数据写 `analysis_result` 并向在线客户端推送 ANALYSIS）。
> 接口依据：`docs/接口规范.md`（字段未做任何改动）。

---

## 1 环境依赖

| 项 | 要求 | 本机实测 |
|---|---|---|
| 操作系统 | Ubuntu 20.04/22.04（VMware 虚拟机，桥接模式） | Ubuntu 20.04.6 LTS |
| 编译器 | gcc（`build-essential`） | gcc 9.4.0 |
| 数据库 | MySQL 8.0 + `libmysqlclient-dev` | MySQL 8.0.42 |
| 运行库 | `libpthread`（glibc 自带）、`libmysqlclient` | — |
| 端口 | **TCP 9000**（非特权端口，**运行服务器不需要 root**） | — |

一次性安装（有 sudo 权限时）：

```bash
sudo apt update && sudo apt install -y build-essential gdb openssh-server mysql-server libmysqlclient-dev
sudo ufw allow 9000/tcp        # 若启用了 ufw；未启用可跳过
```

## 2 数据库初始化（只做一次）

库、表、阈值初始数据与程序用的 `iot` 用户都在 `sql/init.sql` 里。该脚本要建库建用户，**需要 MySQL 的管理员权限**：

```bash
cd ~/server-linux
sudo mysql < sql/init.sql
```

验证（应列出 4 张表与 3 行阈值）：

```bash
mysql -uiot -piot123456 machine_room -e "SHOW TABLES;"
mysql -uiot -piot123456 machine_room -e "SELECT * FROM threshold_cfg;"
```

> MySQL 与 ssh 都是开机自启，**正常开机后无需手动启动**，可用 `systemctl status mysql` 确认。
> 脚本可重复执行（建库建表都是 `IF NOT EXISTS`，阈值是 upsert）。

## 3 编译

```bash
cd ~/server-linux
make            # 产出 ./server
```

`Makefile` 用 `wildcard` 自动收录 `src/*.c`，后续步骤新增模块无需改它。要求**零警告零错误**。
代码有改动时先 `make clean && make`，避免残留目标文件。

## 4 启动与停止

### 4.1 前台运行（推荐日常调试）

```bash
cd ~/server-linux
./server                          # 默认：端口 9000、分析周期 60s、统计窗口 600s
./server -p 9000 -t 60 -w 600     # 显式写法（三项都可省略，省略即用默认值）
./server -t 15 -w 60              # 联调期缩短周期，15 秒就能看到一条 ANALYSIS
```

| 参数 | 含义 | 默认 | 取值范围 |
|---|---|---|---|
| `-p` | 监听端口 | 9000 | 1~65535 |
| `-t` | 分析周期（秒） | 60 | 1~86400 |
| `-w` | 统计窗口（秒） | 600 | 1~604800 |

参数非法（非数字、越界、未知选项）会打印用法并**直接退出**，不会带着坏配置启动。
`-w` 小于 `-t` 时能跑，但相邻两期的窗口不重叠、两期之间的数据不会被统计——只在临时调试时这么用。

成功时输出（启动横幅会打印**实际生效**的端口与周期/窗口）：

```
监听 socket 就绪：0.0.0.0:9000（fd=4, backlog=64）
服务器已就绪，按 Ctrl-C 退出
分析线程已启动：每 60s 统计一次，窗口 600s，仅推送给在线客户端
```

日志直接打在终端上（带时间戳、级别、线程号）。**停止：按 `Ctrl-C`**，会依次打印「select 主循环已退出」→「分析线程已收到退出请求，退出」→「数据库连接已关闭」→「收到退出信号，服务器正常退出」，并释放 9000 端口。

### 4.2 后台常驻（需要腾出终端时）

```bash
cd ~/server-linux
nohup setsid ./server > /tmp/server.log 2>&1 < /dev/null &
tail -f /tmp/server.log          # 看日志；Ctrl-C 只退出 tail，不影响服务器
```

停止后台实例（**用 `-INT` 走优雅退出，且绝不要加 `-f`**）：

```bash
pkill -INT -x server
pgrep -ax server                 # 应无输出
```

### 4.3 开机 / 关机（虚拟机层面）

```bash
# 开机（宿主机执行）
"D:/Virtual Machine/vmrun.exe" start "D:/VMs/Ubuntu/Ubuntu.vmx" nogui

# 关机（先在虚拟机内停服务器，再在宿主机执行）
"D:/Virtual Machine/vmrun.exe" stop "D:/VMs/Ubuntu/Ubuntu.vmx" soft
"D:/Virtual Machine/vmrun.exe" list      # 确认 Total running VMs: 0
```

`soft` 是 ACPI 优雅关机；**不要用 `hard`**（等同拔电源，可能损坏文件系统）。

## 5 自测与联调

### 5.1 确认在听

```bash
ss -ltn | grep 9000               # 应有一行 LISTEN
ip -br addr show ens33            # 当前桥接 IP（校园网 DHCP，可能变动，联调时以实际为准）
```

### 5.2 手测三条标准向量

虚拟机上装有 `nc`，可交互测试（`<>` 内为实际 IP）：

```bash
nc 127.0.0.1 9000
{"type":"LOGIN","client_id":"PC-01"}        ← 应回 {"type":"LOGIN_ACK","status":0}
{"type":"HEARTBEAT"}                        ← 应回 {"type":"HEARTBEAT_ACK"}
```

DATA 向量（见接口规范 §3.3）发出去**不会有应答**（规范未定义应答），要在服务器日志与数据库里看效果：

```
fd=4 client_id=PC-01 DATA：ts=2026-09-28 15:00:01 入库 4/4 行（跳过 0）[1=25.6 2=55 3=312 4=356]
```

```bash
mysql -uiot -piot123456 machine_room -e "SELECT * FROM sensor_data ORDER BY id DESC LIMIT 4;"
# 应看到 4 行（sensor_type 1~4），collect_time 即该条 DATA 的 ts
```

### 5.3 用假客户端跑联调

```bash
# 支持 Python 的机器上（含宿主机），<> 内填虚拟机 IP
python simulator/server_probe.py client -H 10.202.57.4 --id PC-01
```

它每 2s 发一条 DATA（4 个传感器），服务器每条约写 4 行，可在库里查到 `sensor_data` 行数随之增长：

```bash
mysql -uiot -piot123456 machine_room -e "SELECT COUNT(*) FROM sensor_data;"
```

### 5.4 告警自测（S5）

阈值初值：温度 18~26(HIGH)、湿度 40~60(MID)、烟雾 ≤400(HIGH)、**光照不告警**。登录后发一条超标的 DATA，应立即收到 ALARM：

```
{"type":"DATA","ts":"2026-09-28 15:00:01","sensors":[{"id":1,"v":35.2}]}
← {"type":"ALARM","level":"HIGH","sensor":1,"value":35.2,"threshold":26,"msg":"温度超上限","ts":"2026-09-28 15:00:01"}
```

`threshold` 是**被越过的那个边界**（超上限给 max、低于下限给 min）；每条超标 DATA 都告警一次（不去重）。

```bash
mysql -uiot -piot123456 machine_room -e "SELECT * FROM alarm_log ORDER BY id DESC LIMIT 3;"
```

> **改阈值要重启服务器**：`threshold_cfg` 只在启动时读一次（`db_load_thresholds`），改表后需 `pkill -INT -x server` 再 `./server`。

### 5.5 分析结果自测（S6）

服务器每 `-t` 秒（默认 60）统计最近 `-w` 秒（默认 600）的数据，按 `client_id × sensor_type` 聚合写 `analysis_result`，并给**当前在线**的客户端推一条 ANALYSIS（字段见接口规范 §3.1）：

```
← {"type":"ANALYSIS","period_start":"2026-09-22 19:09:29","period_end":"2026-09-22 19:09:29","sensors":[{"id":1,"avg":24.19,"max":29.8,"min":18.1,"std":3.3,"over_count":19}, …]}
```

口径说明（联调时按这几条判读）：

- `avg/max/min/std` 按 `analysis_result` 的列精度（`DECIMAL(10,2)`）规整后推送，**与库里查到的值一致**；
- `std` 在"窗口内只有一个样本"时给 **0**，不是 null；
- `over_count` 是窗口内该组超过阈值的条数，判定口径与 ALARM 完全一致（严格越界、阈值表里为 NULL 的一侧不检查、光照不告警故恒为 0）；
- **无数据的周期不写库、也不推送**（不会给客户端发空的 `sensors` 数组）；
- **不在线的 client 只入库、不推送**：客户端断开后，它窗口内的数据仍会被后续周期统计进 `analysis_result`，只是没人收推送。

排查用 SQL：

```bash
mysql -uiot -piot123456 machine_room -e "SELECT * FROM analysis_result ORDER BY id DESC LIMIT 8;"
```

要核对某一期的统计是否算对了，用那一行的 `period_start/period_end` 手工复现同一窗口：

```sql
SELECT client_id, sensor_type, AVG(sensor_value), MAX(sensor_value), MIN(sensor_value),
       STDDEV_POP(sensor_value), COUNT(*)
FROM sensor_data
WHERE collect_time >= '<period_start>' AND collect_time <= '<period_end>'
GROUP BY client_id, sensor_type;
```

## 6 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `bind() 端口 9000 失败：Address already in use` | 已有实例在跑：`pgrep -ax server` 后 `pkill -INT -x server`（TIME_WAIT 残留由 `SO_REUSEADDR` 处理，不需要等） |
| 队友连不上 9000 | ① `ss -ltn \| grep 9000` 确认在听；② `ip -br addr` 看桥接 IP 是否变了；③ 若启用了 ufw，`sudo ufw allow 9000/tcp` |
| 虚拟机 ping 得通但 ssh 连不上 | `ping` 的统计行会骗人（目标不可达时仍报 0% 丢失），**以 ssh 端口为准** |
| `pkill -f 'server-linux/server'` 把执行命令的 shell 也杀了 | `-f` 匹配整条命令行，连自己一起杀。**只按进程名 `pkill -x server`** |
| 启动即退出，日志 `数据库初始化失败：iot@localhost/machine_room 连不上` | S4 起数据库是**启动硬依赖**：先 `systemctl status mysql` 确认在 running，再确认已执行过 `sql/init.sql`（建库建用户）。认证失败多为脚本没跑过或用户密码不符——`init.sql` 建用户时已显式用 `mysql_native_password`（MySQL 8.0 默认插件会导致登录失败） |
| 启动日志里 `本线程已建立 MySQL 连接` 出现多次 | 正常：S4 起**每个线程一条 MySQL 连接**（主线程 + 4 个工作线程，共 5 条），跑 probe 时 `information_schema.processlist` 里能看到 5 条 `iot` 到 `machine_room` 的连接 |
| 日志 `[ERROR]` 计数看着很多 | 用 `grep -c '\[ERROR\]'` 匹配**级别字段**；`grep 'ERROR'` 会把正文里"回 ERROR code=…"的 INFO/WARN 也算进去（假阳性） |
| 想跑数据竞争/泄漏检测 | 虚拟机没装 valgrind 也能跑：`apt-get download valgrind` + `dpkg-deb -x` 解包到 `/tmp/vg`，用 `VALGRIND_LIB=/tmp/vg/usr/lib/x86_64-linux-gnu/valgrind` 启动。判读：`definitely lost` 为 0 即无泄漏（`possibly lost` 里的 1152 字节是常驻工作线程的 TLS）。**注意 `pkill -INT -x valgrind` 杀不到它**——valgrind 的进程名是 `helgrind-amd64-`（被截断），要用 `pgrep -f '[v]algrind.bin'` 找到 PID 再 `kill -INT <pid>`，valgrind 会把信号转发给服务器，走完优雅退出后才会写完整报告 |
| 日志停在「分析：窗口 … 内无数据，本周期不写 analysis_result」 | 正常：该窗口内一条 DATA 都没有（客户端都断了、旧数据也过了窗口），既不写库也不推送 |
| 客户端收不到 ANALYSIS | 依次查：① 这台客户端在窗口内有没有数据（刚登录的要等下一个有数据的周期）；② 连接是否还活着（推送只发给当前在线的会话）；③ `ps -ef \| grep server` 看实际启动参数，确认 `-t/-w` 没被改小 |

更多排查过程见 `docs/调试记录-C.md`（S0~S3 的每个坑都有"现象→定位→原因→解决"）。
